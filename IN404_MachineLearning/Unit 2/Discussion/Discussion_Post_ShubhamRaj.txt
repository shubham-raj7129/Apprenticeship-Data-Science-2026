**Structured and Unstructured Data**

From what I have learned, structured data is data that is organized in a predefined format—it fits neatly into rows and columns with a fixed schema (Jonker & Gomstyn, n.d.). The first use case I think of is a hospital's electronic health records database, where each row represents a patient and columns hold attributes like age, blood pressure, and diagnosis code. Another example I find useful is financial transaction logs, where every purchase is recorded with a timestamp, amount, merchant, and account number. I noticed that because structured data is already tabular, I can feed it into machine learning models with relatively little preprocessing, which makes it much more straightforward to work with.

Unstructured data, on the other hand, does not follow a predefined structure, and I was surprised to read that it accounts for roughly 90% of all enterprise-generated data (Jonker & Gomstyn, n.d.). One use case that I find fascinating is sentiment analysis of customer reviews—raw text has to be converted into numerical representations before a model can classify reviews as positive or negative. Another powerful use case is medical image analysis, where convolutional neural networks are trained on X-rays or MRI scans to detect tumors. What stands out to me is that extracting insights from unstructured data typically requires more advanced techniques like NLP or deep learning, which makes it significantly harder to handle than structured data.

**Qualitative and Quantitative Data**

Qualitative data, also called categorical data, describes categories or characteristics rather than measurable quantities. For example, in a customer churn prediction model, I would treat the subscription plan type (basic, standard, or premium) as qualitative data to help identify behavioral patterns across groups. Another use case I have seen is spam email detection, where the presence or absence of certain keywords serves as categorical features for classification. What I found important is that qualitative data needs to be encoded—using techniques like one-hot encoding or label encoding—so that ML algorithms can work with it numerically (Donges, 2025).

Quantitative data represents measurable numerical values, and I find it generally more intuitive to work with. In a real estate price prediction model, for instance, I would use features like square footage, number of bedrooms, and lot size—all quantitative—and feed them directly into a regression algorithm. Another example that interests me is predictive maintenance in manufacturing, where sensor readings like temperature, vibration frequency, and pressure are continuous quantitative measurements used to predict equipment failure. I have noticed that even though quantitative data is easier for models to handle directly, it still benefits from normalization or standardization to ensure balanced feature contributions.

**Levels of Measurement and Appropriate ML Methods**

The four levels of measurement—nominal, ordinal, interval, and ratio—further refine how I think about handling data in machine learning.

Nominal data consists of categories with no inherent order, like eye color, country of origin, or product category. Since there is no ranking relationship, I would use classification algorithms like decision trees, random forests, or naive Bayes, which can split data based on category membership without assuming any ordinal relationship. I learned that one-hot encoding is the standard preprocessing step here to avoid implying a false ordering (Donges, 2025).

Ordinal data has a meaningful order, but the intervals between categories are not necessarily equal. Education level (high school, bachelor's, master's, doctoral) and customer satisfaction ratings (poor, fair, good, excellent) are examples I find helpful. For ordinal data, I would lean toward tree-based methods like gradient boosting and random forests, which respect the order without requiring equal spacing. Logistic regression with label encoding can also work well here since the encoded integers preserve the rank order.

Interval data has equal intervals between values but lacks a true zero point. Temperature in Celsius is the classic example I keep coming back to—the difference between 20°C and 30°C is the same as between 30°C and 40°C, but 0°C does not mean "no temperature." SAT and IQ scores also fall into this category. I think interval data is well-suited for linear regression, support vector machines, and k-nearest neighbors, since all of these rely on meaningful distance calculations between data points. I would typically apply standardization here to make sure features on different scales contribute equally.

Ratio data has both equal intervals and a true zero point, which means ratios between values are actually meaningful. Examples I find easy to remember include income, weight, age, and distance traveled. What I appreciate about ratio data is that it supports the full range of mathematical operations, so it is compatible with virtually all ML methods—linear and logistic regression, neural networks, clustering algorithms like k-means, and dimensionality reduction techniques like PCA. The true zero lets a model interpret proportional relationships (for example, earning twice as much or traveling half as far), which I think is particularly valuable in regression and forecasting tasks.

**Real-World Application: Healthcare Fraud Detection**

To tie all of these concepts together, I thought about a machine learning system designed to detect fraudulent healthcare insurance claims—this application touches nearly every data type I discussed above. The structured data includes the claims database itself, with fields like patient ID, procedure codes, billed amount, and provider number. The unstructured data comes in the form of physician notes, scanned documents, and call center transcripts that may reveal suspicious patterns. I would identify qualitative features like the type of procedure (nominal) and the urgency classification of a visit (ordinal), alongside quantitative features like the dollar amount billed (ratio) and the number of procedures per visit (ratio).

If I incorrectly treated ordinal urgency levels as nominal, I would lose valuable information about the severity ranking and might miss patterns where fraudsters consistently classify visits at a higher urgency to inflate reimbursements. Conversely, if I treated nominal procedure codes as ordinal by label-encoding them, I would introduce a false ordering that misleads the model into thinking procedure code 500 is somehow "greater" than code 100—which makes no sense.

One transformation challenge that I find really interesting involves the unstructured physician notes. Using NLP techniques like TF-IDF or word embeddings, I could convert those notes into structured numerical features—essentially turning unstructured qualitative data into structured quantitative data that a supervised learning classifier can use alongside the tabular claims data. I think this is a great example of how understanding data types is not just theoretical; it directly shapes the decisions I would make in a real ML pipeline.
